【知识点总结】运维

  • 运维管理平台

    • 服务编排，实现一键部署，启动后发送请求给测试的自动化任务，进行投产后的测试

    • 资产管理

    • 日报统计 发送给开发前一天的服务接口访问量，失败率，接口请求时间等。发送给作为整个平台的接口情况，还有cdn使用量等等

    • 事件管理 把每次告警进行分级和分类，查询当时关联的实例资源情况，pod副本，中间件连接状况，展示在一个大屏。尽可能展示出事件的原因

    • 异步任务 重构

      • 反射 getattr 通过使用某个对象的方法或者属性字符串名称来调用该对象的属性和方法

      • 使用了celery 来实现异步通知或调用其他功能模块

      • 使用APscheduler执行计划任务，代替之前的crontab的方式

  • 降本增效

    • 突发型实例，成本降低50%以上
    • 节省计划，能达到预付费的价格
    • 资源混部。大数据离线任务一般在后半夜，而服务的高峰期一般在白天。
    • 阿里云编排策略，在高峰期实现自动或手动扩容和收缩
    • 配置pod limits和requests参数，限制服务最大资源要求防止资源使用不均衡；保障最小资源要求，防止资源不足而产生超时或行为优先级低而被删除的情况

  • 告警

    • 日志平台的接口失败率告警，状态码
    • 微服务的健康检查接口，定时循环遍历
    • 服务pod副本数量和状态告警
    • 业务告警，配合开发人员的sql，或者日志关键字
    • 慢sql趋势告警，同步显示实例信息，负载信息，对比昨日

  • 日志机制

    • 服务日志通过计划任务处理转移到Nas指定位置。
    • 平台依据服务名和项目组向负责人发送邮件，邮件中包含日志链接和授权码
    • 最好的方式是存储在elk平台，方便实时查询，也可以通过业务日志关键字来发出一些告警

  • 飞书机器人

    • 建立飞书群，添加机器人，会有一个webhook地址，调用这个地址，就会向对应的飞书群发送消息
    • 消息类型可以是文本，也可以是卡片。如果是卡片的话还可以执行更多交互，比如点击按钮或者选择菜单会执行一系列操作。
    • 另外一个很有用的功能是可以和机器人交互，比如发送文字指令，间接进行一系列的指令操作。这个指令需要提前写好功能模块的
    • 可以实现输入服务名自动发布。输入实例名自动回复当前负载信息，输入k8s自定义指令实现服务的伸缩

  • Prometheus AlterManager 报警抑制

    • 分组 将类似性质的警报分类为单条通知。比如许多系统宕机会触发成百上千的警报。这时候会合并成一条报警，比如10s内有多条
    • 抑制 当警报发出后，停止重复发送由此警报引发的其他警报
    • 静默 特定时间不告警的机制，可以在web控制台操作

管理岗

运维体系建设

1. 明确运维团队的目标和职责

核心目标：保障业务系统的稳定、高效、安全、低成本的运行，并支撑业务的快速迭代与创新。

运维团队常见职责包括：

领域主要职责
基础设施运维服务器、网络设备、IDC/云资源管理、操作系统维护等
应用运维（SRE/应用保障）应用部署、配置管理、服务治理、发布与回滚、服务稳定性保障
监控与告警系统/应用监控、日志收集、指标分析、异常告警与响应
自动化运维脚本工具开发、CI/CD 流水线、基础设施即代码（IaC）、批量运维
安全运维主机安全、网络安全、权限管理、漏洞修复、合规审计
备份与灾备数据备份策略、容灾演练、故障切换、业务连续性保障
运维流程与规范变更管理、事故管理、问题管理、发布流程、权限控制等 SOP
成本管理云资源成本优化、容量规划、资源利用率分析

2. 运维体系的组成

2.1. 运维流程和规范体系

目的：让运维工作标准化、可重复、可追溯，降低人为风险。

流程说明
变更管理所有线上变更（如部署、配置、网络调整）需通过工单/流程审批，评估影响与回滚方案。
发布管理应用发布流程（灰度→全量）、版本控制、回滚机制。
事故管理（Incident Management）故障响应、定位、恢复、事后复盘（Postmortem）。
问题管理（Problem Management）针对重复故障，挖掘根因并彻底解决。
配置管理基础设施与应用的配置项版本控制（如 Ansible、Terraform 管理）。
权限与访问控制最小权限原则，操作审计，敏感操作二次审批。

✅ 推荐引入 ITIL 流程思想（如事件、问题、变更、配置管理），并根据企业实际简化落地。

2.2. 监控与可观测性体系（Observability）

目的：让系统“看得见、看得懂”，快速发现与定位问题。

监控体系通常包括：

监控维度工具举例说明
基础设施监控Prometheus、Zabbix、DatadogCPU、内存、磁盘、网络、节点状态
容器 & Kubernetes 监控Prometheus + kube-state-metrics + cAdvisorPod、Node、Deployment、Service 状态
应用性能监控（APM）SkyWalking、Pinpoint、Jaeger、New Relic应用性能、链路追踪、慢请求
日志监控ELK（Elasticsearch+Logstash+Kibana）、Loki、Graylog收集、存储、检索、分析日志
业务指标监控Prometheus、Grafana、自定义 Exporter如订单量、支付成功率、用户活跃数
告警管理Alertmanager、PagerDuty、钉钉/企业微信机器人告警收敛、分级通知、值班响应

🎯 目标：从“监控可用性”走向“可观测性”（Metrics + Logs + Traces）。

2.3. 自动化运维体系（DevOps / IaC）

目的：减少人工操作，提升效率、一致性与可靠性。

自动化范围包括：

自动化领域工具/实践说明
基础设施自动化Terraform、Ansible、CloudFormation云资源创建、配置管理
配置管理Ansible、SaltStack、Puppet批量配置服务、软件安装
部署与发布自动化Jenkins、GitLab CI/CD、ArgoCD、Spinnaker代码构建、测试、发布流水线
批量运维与脚本工具Shell/Python 脚本、Ansible Playbook批量执行、日常任务
基础设施即代码（IaC）Terraform、Crossplane通过代码定义云资源，版本控制、可审计
自助化平台内部 CMDB、运维平台、审批流、资源申请系统提升效率，减少重复劳动

✅ 建议：推动“一切可脚本化、一切可自动化”，减少人为失误。

2.4. 安全运维与合规体系

目的：保障系统的安全性、数据的保密性与完整性，符合行业监管要求。

常见工作包括：

  • ∙主机安全：漏洞修复、基线检查、防火墙策略。
  • ∙网络安全：VPC、安全组、访问控制、流量加密。
  • ∙应用安全：权限控制、接口鉴权、防止注入/越权。
  • ∙数据安全：敏感数据加密、脱敏、备份与访问审计。
  • ∙权限与身份管理：RBAC、最小权限、多因素认证、操作审计。
  • ∙合规与审计：等保 2.0、GDPR、ISO 27001、内部安全巡检。

✅ 建议：安全左移（DevSecOps），将安全融入 CI/CD 与运维流程中。

2.5. 灾备与高可用体系

目的：保障业务连续性，在故障发生时快速恢复。

关键措施：

  • ∙高可用架构：多可用区、多集群、服务冗余、负载均衡。
  • ∙容灾演练：定期模拟故障，验证容灾与切换能力。
  • ∙数据备份：定期备份数据库、配置、日志，验证可恢复性。
  • ∙故障切换与回滚：数据库主从切换、服务降级、流量调度。
  • ∙容量规划：预测业务增长，提前扩容，避免资源瓶颈。

✅ 建议：制定并演练 RTO（恢复时间目标） 与 RPO（恢复点目标）。

一个完善的运维体系 = 标准化的流程 + 全面的监控与可观测性 + 高效的自动化工具 + 严格的安全管控 + 健壮的容灾能力 + 专业且协作的团队。

监控体系

监控的定义：通过采集、聚合、分析与展示系统或应用的各项指标、日志、调用链路等数据，实时或接近实时的掌握运行状态，以便于：

  • 发现潜在异常或危险
  • 快速定位故障根因
  • 评估系统性能和资源使用情况
  • 支撑容量规划与业务决策

简单说：监控就是让系统“看得见”、让问题“看得清”、让运维“做得准”。

核心目标与价值

核心目标：

  1. 保障系统稳定性：及时发现故障，缩短 MTTR（平均修复时间）。
  2. 提升系统可靠性（SLA/SLO）：通过监控关键服务质量指标，确保承诺的服务可用性。
  3. 优化性能与资源使用：发现性能瓶颈，合理利用 CPU、内存、网络等资源。
  4. 支持容量规划：基于趋势预测未来资源需求，避免不足或浪费。
  5. 增强安全性与合规性：通过日志与行为监控，发现异常访问与操作。
  6. 辅助业务运营：通过业务指标（如订单量、用户活跃度）监控，反映产品健康状态。

监控的价值体现：

  • 对 运维团队：减少故障发现与响应时间，提升运维效率与系统可用性。
  • 对 开发团队：帮助快速定位代码或服务问题，提升发布质量与迭代速度。
  • 对 SRE/平台团队：通过可观测性数据驱动系统稳定性与效能提升。
  • 对 管理层：通过关键业务指标大盘，辅助决策与风险控制。

监控系统的分层

一个完善的监控体系通常是分层设计的，覆盖从基础设施到业务应用的全栈：

层级监控对象监控内容说明
1. 基础设施层服务器、网络设备、存储、IDC/云资源CPU、内存、磁盘、网络、负载、温度等保障硬件与底层资源稳定
2. 系统软件层操作系统、容器、虚拟化平台、中间件进程状态、容器资源、服务可用性、网络连接等如 Docker、Kubernetes、Nginx、MySQL
3. 应用服务层后端服务、API、微服务接口响应时间、错误率、吞吐量、业务逻辑异常等应用自身状态与性能
4. 业务层业务功能、用户行为、交易数据订单量、支付成功率、用户活跃数、转化率等反映业务健康度与运营状态
5. 安全层用户行为、访问控制、异常登录、数据泄露登录异常、权限变更、API 调用异常等安全监控与风控

建设原则

  1. 从业务出发，以稳定为核心：围绕业务关键路径与用户体验构建监控。
  2. 分层监控、逐层深入：从基础设施 → 系统 → 应用 → 业务，逐层细化。
  3. 指标可量化、可聚合、可告警：定义清晰的监控指标与健康标准。
  4. 告警有分级、有归属、有响应：避免告警泛滥，确保“告警必有人跟”。
  5. 可视化直观、大盘清晰：关键信息一目了然，支持多维度分析。
  6. 自动化与智能化：减少人工干预，提升效率与准确性。
  7. 持续优化与演进：随业务发展不断调整监控策略与覆盖范围。

监控体系是 IT 系统的“眼睛”和“神经系统”，它通过 Metrics、Logs、Traces 等数据的采集与分析，实现对系统运行状态的实时感知、异常发现、问题定位与辅助决策。一个完善的监控体系应当是分层设计、全栈覆盖、业务关联、实时可视、智能告警、可扩展演进的，它是保障系统稳定性、提升运维效率、驱动业务健康发展的关键基础。

基础知识准备不足

  • Header

  • cache

  • cookies

  • Accept 表示浏览器客户端可以接受的媒体类型，比如html/json

  • Accept-Encoding 支持压缩

  • Accept-Language 接受的语言

  • User-Agent 浏览器告诉服务器，客户端使用的操作系统、版本、CPU类型、浏览器版本等

  • Connection 保持连接时长

  • Refer 让服务器判断来源页面

  • Host 指定被请求主机和端口号

  • 数据库索引

  • 用途，避免全表扫描，提高数据库的查询性能，但是会占用额外的磁盘空间，修改数据时也需要进行索引的维护。

  • 类型（物理存储角度）

  • 聚集索引（主键索引），按照一个特定维度排序存储；

  • 非聚集索引，给普通字段加上索引，通过二叉树的数据结构来描述的，随机存储

  • 联合索引，多个字段组成的索引

  • TCP/IP 模型

  • 应用层 提供常见的网络应用服务，包含的协议主要有HTTP、FTP、SSH、SMTP、POP3等

  • 传输层 提供应用传输间的通信，包括格式化信息流和提供可靠传输。包含的网络协议TCP、UDP

  • 网络层 处理网络上流动的数据包，规定了怎样的路径把数据包传输到目标计算机，并把数据包传给对方。包含IP、ARP、ICMP

  • 网络接口 用了处理连接网络的硬件部分，使硬件遵循一个标准，以便相互连接。

  • OSI模型

  • 应用层 直接想用户提供服务, APDU

  • 表示层 负责数据格式的转换，将应用处理的信息转换为适合网络传输的格式。 SSL、ASCII，PPDU

  • 会话层 建立和管理应用程序直接的通信 RPC，SPUD

  • 传输层 监控数据传输服务的质量，保证报文的正确传输 TCP、UDP，TPDU

  • 网络层 通过路由选择算法，为报文通过通信子网选择最合适的路径。路由器、三层交换机 IP、ICMP，报文

  • 数据链路层 建立逻辑连接，进行硬件地址寻址、差错校验等功能。交换机、网卡 PPP，帧

  • 物理层 建立和维护物理连接。比如网线，比特

  • time_wait

  • 原因

  • 服务端大量close_wait的连接没有及时关闭，在高并发短连接的HTTP请求下，客户端不断发出新的连接请求。打开的文件描述符会不断增加。打开达到上限后就无法新建socket来响应新的请求。

  • 解决方案

  • 修改内核参数，开启syn cookies,出现syn等待队列溢出时，启用cookies处理，减少syn攻击。尽量把syn请求缓存起来，等待有能力处理的时候处理tcp的连接请求

  • 开启重用，允许将time_wait 的socket用于新的tcp连接

  • 开启快速回收，socket的快速回收

  • 修改默认time_out时间

  • 客户端，HTTP请求头，设置为keep-alive

  • 应用层避免频繁关闭连接，比如使用长连接

  • Pod创建历程

  1. 用户使用yaml创建pod,请求转发给APIServer，APIServer 将的yaml中的属性信息写入etcd

  2. APIServer watch机制准备创建pod,将信息转发给scheduler。scheduler 通过调度算法进行node的预选，过滤掉不符合要求的主机；然后进行调度优选，对上一步筛选出来符合的主机进行打分。最终选择打分最高的主机，并将node信息反馈给APIServer，APIService将绑定的node信息写入etcd

  3. APIServer 通过watch机制，调用Kubelet，指定pod信息。触发docker run，创建容器

  4. 创建完成后将pod信息反馈给kubelet,kubelet将pod信息返回给APIServer，APIServer将pod的状态信息写入etcd

  5. Kubelet get pods 调用etcd中的信息，这时候就能展示出来pod的列表

  • 组件关系

  • APIServer 提供kubernetes API

  • Etcd 兼具一致性和高可用性的键值数据库，保存集群中所有信息的数据库

  • Kube-scheduler 负责监视新创建的、未指定运行节点的pod,进行pod的调度

  • 数据类型：string、hash、list、Set 无序，不能重复、Zset 有序，不能重复

  • Redis 内存不足的淘汰策略

  • 算法

  • LRU 根据数据的历史访问记录来淘汰数据，如果最近被访问过，那么将来被访问的几率也更高

  • LFU 根据最近访问的频率进行排序，频率低的优先被删除，Redis 4.0以后出现的

  • 策略

  • Volatile-lru 利用LRU算法溢出设置过过期时间的key

  • Allkeys-lru 利用LRU算法溢出任何key，删除的key 包括设置过期时间和不设置过期时间的 通常采用该方法

  • Volatile-random 移除设置过过期时间的随机key

  • Allkeys-random 无差别的随机移除

  • Volatile-LFU 设置了过期时间的key 使用LFU算法淘汰

  • Allkeys-LFU 如果一个key最近一段时间内使用次数很少，那么将来被使用的可能性就很小

  • Volatile-ttl 移除即将过期的key

  • Noevicition 不移除任何的key，只返回写错误，默认选项

  • MySQL的主从复制原理

  • master节点将数据变化记录写入到二进制日志binlog；

  • slave服务器会在一定时间间隔内对master的binlog探测是否发生改变，如果改变则开始一个I/O线程请求master 发送binlog里的更新记录到从库上；

  • 主节点生成log dump线程，给从库I/O产出传输binlog写入中继日志；

  • 从节点开启SQL线程，读取中继日志，并写入到数据库中

  • 三次握手

  • 1.客户端发送 SYN=1，SEQ=X到服务器，表示请求建立新连接，客户端进入syn-sent阶段

  • 2.服务器收到TCP报文后结束Listen状态，返回一段报文，SEQ=y,ACK=x+1,SYN=1,服务器进入SYN-RCVD阶段

  • 3.客户端接收到服务器确认的TCP报文后，明确客户端到服务器数据传输是正常的，结束SYN-SENT阶段，返回最后一段报文。ACK=1，SEQ=X+1，ACK=y+1。客户端进入established阶段。

  • 服务器收到客户端确认收到服务器数据的报文后，明确服务器到客户端的数据传输正常，结束SYN-SENT阶段，也进入established接。

  • traceroute 原理

  • 使用ICMP协议定位本机和目标主机之间的所有路由器。IP路由过程中对数据包TTL的处理。

  • 当路由器收到一个IP包时，会改动IP包的TTL，没收到一个包，就会检查这个包的TTL是否为1或者0。如果是0则表名没到目的地，并且剩余时间不多了，肯定到不了目的地，因此丢弃这个包，并给源主机发送ICMP通知，表明包已超时。ICMP的通知信息里包含当前路由器发送时所用的IP。

  • P1的TTL设置为1，到达R1时，TTL减1。由于TTL等于0，R1把P1丢弃并向源主机发送一个ICMP超时报文

  • P2的TTL设置为2，到达R1后减1，继续走到R2，R2收到后TTL减1为0。R2丢弃P2，返回给源主机ICMP不可达的报文
