【kubernetes】Docker和Containerd的关系

发表于 2025-05-15 分类于 云原生 阅读次数：

前言

2020 年 12 月，Kubernetes 1.20 发布。Kubernetes 社区宣布 dockershim（Docker 的适配层）被标记为“已废弃”（deprecated），鼓励用户迁移到 Containerd 或 CRI-O 等直接支持 CRI 的运行时。这标志着 Containerd 正式成为 Kubernetes 推荐的容器运行时之一。虽然不是 Kubernetes 的内置组件，但它是 Kubernetes 生态中的主流选择。

自 Kubernetes 1.24 起，Docker 的 dockershim 支持被移除，Kubernetes 不再直接支持 Docker 作为运行时。Kubernetes 完全移除 dockershim，Docker 不再作为默认运行时。Containerd 和 CRI-O 成为 Kubernetes 的主要运行时选择。

那么Containerd到底是什么？作为一个多年前只属性Docker的运维人来说Containerd这个概念很陌生，接下来就了解一下。

基本概念

首先聊一下什么是容器运行时（Container Runtime）？

容器运行时（Container Runtime）是负责管理容器生命周期的软件组件，它在容器化技术中扮演核心角色，负责创建、运行、停止和删除容器。以下是对容器运行时的详细解释：

定义

容器运行时是一个软件层，负责与操作系统内核交互，管理容器的创建和执行。它通过调用内核的隔离技术（如 Linux 的 namespaces、cgroups 和 seccomp）来实现容器的隔离、资源分配和安全管理。

主要功能

容器运行时通常负责以下核心任务：

  1. 镜像管理：从镜像仓库拉取容器镜像，解压并准备镜像内容。
  2. 容器创建：根据容器镜像创建容器，包括设置命名空间（network、PID、mount 等）以隔离容器环境。
  3. 资源分配：通过 cgroups 控制容器的 CPU、内存、磁盘等资源。
  4. 容器生命周期管理：启动、暂停、停止、删除容器。
  5. 网络和存储配置：为容器配置网络接口和存储卷。
  6. 安全隔离：通过内核安全机制（如 seccomp、AppArmor 或 SELinux）确保容器之间的隔离和安全性。

容器运行时的分类

根据功能范围，容器运行时可以分为两类：

  1. 低层次运行时（Low-Level Runtime）：
    • 专注于底层的容器执行，例如创建 namespaces 和 cgroups。
    • 示例：runc（OCI 标准实现，Containerd 的默认低层次运行时）。
  2. 高层次运行时（High-Level Runtime）：
    • 提供更高级的功能，如镜像管理、API 接口等，通常调用低层次运行时来执行容器。
    • 示例：Containerd、CRI-O。

容器运行时与 Docker 的关系

  • Docker 早期使用自己的运行时（libcontainer），后来将其贡献给 OCI（开放容器倡议），成为 runc。
  • Docker 内部使用 Containerd 作为高层次运行时，Containerd 再调用 runc 来执行容器。
  • 其他工具（如 Kubernetes）可以直接使用 Containerd 或 CRI-O，绕过 Docker 的完整堆栈。

常见容器运行时

  1. runc：
    • 符合 OCI（Open Container Initiative）标准，是最广泛使用的低层次运行时。
    • 轻量、专注于容器执行，常被高层次运行时调用。
  2. Containerd：
    • 高层次运行时，支持镜像管理和 CRI 接口，广泛用于 Kubernetes。
    • 比 Docker 轻量，专注于运行时核心功能。
  3. CRI-O：
    • 专为 Kubernetes 设计的运行时，直接支持 CRI 接口，轻量且模块化。
  4. Docker：
    • 虽然 Docker 本身是一个完整的容器平台，但其运行时部分依赖 Containerd 和 runc。
  5. Kata Containers：
    • 提供虚拟化容器运行时，通过轻量级虚拟机增强隔离性，适合安全敏感场景。

与 Kubernetes 的关系

Kubernetes 通过 CRI（Container Runtime Interface）与容器运行时交互。CRI 是一个标准接口，允许 Kubernetes 使用不同的运行时（如 Containerd、CRI-O）。自 Kubernetes 1.20 起，Docker 不再作为默认运行时，Containerd 和 CRI-O 成为主流选择。

总结

容器运行时是容器技术的核心，负责管理和执行容器，确保隔离性和资源分配。Containerd 是一个高层次运行时，Docker 则是一个包含 Containerd 的更完整平台。选择运行时取决于场景：开发测试用 Docker，生产集群用 Containerd 或 CRI-O 更高效。

简单理解

Containerd 和 Docker 的关系及区别

可以把 Docker 比作一个“全能管家”，而 Containerd 就是这个管家里面的“仓库管理员”。

1. 关系

  • Docker 是一个完整的容器管理工具，它包含了：
    • Docker CLI（命令行工具）：你平时用的 docker run、docker ps 等命令。
    • Docker Engine（引擎）：负责管理容器的生命周期（创建、运行、停止等）。
    • Containerd：Docker 引擎底层的一个核心组件，专门负责管理容器的运行时（Runtime），比如启动、停止容器，管理镜像等。
    • 其他工具：如 Docker Compose、Docker Swarm 等。
  • Containerd 是 Docker 的一个子项目，后来独立发展，成为一个标准的容器运行时（Runtime），可以被 Kubernetes 等工具直接调用。

简单来说：

  • Docker = 整个厨房（包含厨师、食材、工具）
  • Containerd = 厨房里的冰箱（专门管理食材和存储）

2. 使用时的区别

对比项DockerContainerd
定位完整的容器管理工具（CLI + 引擎 + 运行时）专注于容器运行时的底层组件
适用场景开发、测试、本地运行容器生产环境、Kubernetes 等编排系统
依赖关系包含 Containerd可以独立运行，不依赖 Docker
命令行docker run、docker ps需要 ctr 或 nerdctl（类似 Docker CLI 的工具）
与 Kubernetes 集成需要额外配置（如 dockershim，已逐步淘汰）直接支持（Kubernetes 原生支持 Containerd）
功能提供完整的容器生命周期管理（镜像构建、运行、网络等）只负责容器的运行时管理（启动、停止、删除容器）

3. 为什么 Kubernetes 更推荐 Containerd？

  • 更轻量：Containerd 只做容器运行时，不包含 Docker 的额外功能（如镜像构建），启动更快，占用资源更少。
  • 更稳定：Kubernetes 直接调用 Containerd，减少中间层（如 dockershim），降低故障风险。
  • 更标准化：Containerd 是 CNCF（云原生计算基金会）项目，符合云原生标准，适合大规模生产环境。

如果你是开发者，平时用 docker run 测试应用，就用 Docker。
​​如果你是运维/集群管理员​​，在 Kubernetes 上运行容器，直接用 Containerd 更高效。

总结

  • Docker = 全能工具箱（适合开发、测试）
  • Containerd = 专业工具（适合生产、Kubernetes）

现在很多云服务器和 Kubernetes 集群都直接使用 Containerd，而不再依赖 Docker，因为更轻量、更稳定！ 🚀

使用的异同？

场景DockerContainerd
快速运行容器docker run -d nginx（简单直观）ctr run –net-host docker.io/library/nginx:latest my-nginx（复杂，需手动配置）或用 nerdctl run
构建镜像docker build -t my-image .（内置支持）无直接构建功能，需用 BuildKit 或 nerdctl build
查看容器状态docker ps（清晰直观）ctr container ls（信息较原始）或 nerdctl ps
网络管理docker network create（内置支持）需外部工具（如 CNI 插件）配置网络
生产环境适合小型或单机部署适合 Kubernetes 集群，性能优异
学习曲线低，适合初学者高，需熟悉底层机制或依赖 Kubernetes
